## 2. 先认识软件实际修改的东西
- **DWG 文件**：一个容器，可以装很多张图。
- **模型空间**：一般保存实际绘图对象。
- **布局空间**：用纸张、视口组织出图。视口像观察模型的窗口，不等同于图形本身。
- **图框**：外围边框、规格和相关结构。
- **图签**：记录图名、图号、项目、人员、日期等信息的区域。
- **块定义 / 块参照**：前者像模具，后者是放进图中的具体实例。同一个定义可以在不同位置、缩放和旋转下使用多次。
- **属性文字**：附在块实例上的可填写文字。标签“图名”用来找对象，显示内容“图纸目录”是对象的值。
- **外部参照 XREF**：显示内容来自另一份文件。宿主 DWG 存在，并不证明外参文件也存在。
- **组 GROUP**：把对象组织起来方便选择；它与块、外参不是同一种结构。看到“成组”现象，不能直接推断程序一定按组处理。
- **句柄**：图中对象的标识。验收可利用它检查对象是否仍存在，但句柄未变化不能证明其所有几何属性都没变化。
- **富文本指令**：文字内容中控制字体、宽度、换行等的标记，例如反斜线 P 表示段落。它们不是普通可见文字。

这套软件主要依据 CAD 对象类型、属性标签、空间、尺寸、位置和预设规则工作。当前阅读的主处理链路中没有依靠大语言模型看图判断图框的步骤。因此，图纸结构超出规则时，需要兼容处理或人工核对。

## 3. 从启动到结果，底层怎样工作

```text
启动程序
  ↓
激活授权检查、更新检查
  ↓
WPF 界面选择目录、扫描、填写统一信息和逐图信息
  ↓
C# 核心组织批次和字段表
  ↓
PowerShell 调用本机 AutoCAD Core Console
  ↓
LISP 读取 DWG：识别图框、图签、字段及模型/布局位置
  ↓
人工核对不确定项
  ↓
按处理模式修改输出 DWG
  ↓
独立重扫输出 → 比较源清单、处理计划和成果
  ↓
界面显示通过、待核对或失败，并提供报告
```

### 3.1 启动和授权
正式构建后，先判断许可是否有效，再进行更新检查和打开主窗口。授权检查既在启动层，也在扫描、处理入口处。

一个容易误解的细节：这些调用有一部分由 build.ps1 在构建临时源码时注入。因此只打开原始 Program.cs，可能看不到最终程序完整的启动授权顺序。构建脚本找不到预期入口时会报错，不会默默跳过授权注入。

### 3.2 扫描
核心的 ScanAsync 调用 run_frame_replacement.ps1，但不传 -Apply，并启用 CombinedInventoryDirectory。也就是先做一次合并的“只扫描、不执行替换”，同时取得字段和验收清单，当前界面传入最多 2 个并行工作任务。

所以脚本名称含 replacement，不代表扫描按钮已经换图框。旧开发文档把扫描描述成直接调用 scan_all_frames.ps1，属于较概括、部分滞后的说明；最新实际入口以代码为准。scan_all_frames.ps1 仍用于独立扫描，尤其是成果复扫。

扫描结果按图签/图纸组织成表格。一份 DWG 可以产生多行，不是“一份文件必定一行”。输入目录检查使用 TopDirectoryOnly，不能假设所有子文件夹也被递归处理。

### 3.3 统一信息和逐图信息
界面输入先进入 C# 字段和数据表，再写成处理脚本可读取的字段文件。统一信息用于批量设置，逐行字段用于具体图纸；最终处理读取的是合并后的字段值，不是直接从屏幕截图取字。

切换目录时 LoadBatchDirectory 清空旧批次图纸行、选择、日志和会话状态，没有同时清空统一信息与人员姓名控件。保留的是当前程序会话中的输入；不能据此承诺关闭重开后仍永久保存全部输入。

统一信息“一键清空”和人员姓名“一键清空”清的是输入控件。空白通常表达保留原值。它们不能与签字 DWG 的“明确清除”混为一谈：后者有专门清除标记 __CFR_CLEAR_SIGNATURE__，可要求删除对应签字。

### 3.4 实际处理
ApplyAsync 再次检查条件，锁定本批次字段，调用 run_frame_replacement.ps1 并传 -Apply。调度器安排逐文件任务，replacement_worker.ps1 启动 Core Console，加载 replace_frames.lsp 执行修改。

程序区分两种主要模式：
- Replace：替换图框，并处理对应图签。
- UpdateTitle：仅更新图签。位于外参内部的图签不一定能安全原位写入，代码会提示改用替换模式或核对。

新框、图签不是靠界面画出来，而是使用 engine/assets 的 DWG 素材插入。LISP 负责匹配旧对象、确定目标、写属性、处理签字和部分代理/外参/散文字兼容情况。它并非只把整张图“另存一次”。

### 3.5 最新文字保留逻辑
对具有可靠原本地图签属性的情况：
1. 新图框继续使用原图框的插入点、X/Y 缩放和旋转。
2. 新图签读取原图签**自身**的插入点、X/Y 缩放和旋转，不再把图框参数当然地当作图签参数。
3. 图名、图号分别读取原属性实例的数据，保留文字几何和相关格式，再写入需要的文字内容。
4. 签字图块的定位和缩放使用对应图签参数。

例如原图签缩放是 150.00001811，内部保留完整原值；界面显示简化不应改变内部数值。每个实例独立读取，不能按文件名、单一样本或固定字号套用。

**这不等于所有文字的全部情况已经解决。** 当前明确的原属性几何保留针对图名、图号；其他项目字段、散文字、代理或虚拟图签存在不同处理分支。原图本身越框、缺失字体、外参文件缺失等，也不是仅复制两个属性就会自动解决。最新版本说明明确记录：富文本重复指令及相关判红尚未在本轮修复。

### 3.6 验收和红黄结果
处理结束后，核心调用独立扫描，再运行 verify_replacement.ps1。它比较计划、源对象与输出对象，检查数量、字段、部分人员/签字要求、布局及块的变换参数、规划外对象句柄等。

其中插入点、缩放、旋转等比较仍严格要求一致。最新修复是让写入结果保留原参数，不是把验收差异放过去。

- **黄色**：通常意味着待人工核对、识别不充分或不能自动完成全部工作，具体原因以本行状态为准。
- **红色**：可能是执行失败，也可能输出存在但未通过验收。不同原因不能合并成“文件坏了”。
- **通过**：表示当前检查规则通过，不等于逐像素视觉比对、所有外参可用、所有文字边界及所有 CAD 实体属性都已被证明完全相同。

界面 FailureExplanation 把技术结果翻译成易懂说明，原始 TechnicalResult 继续保留。改提示语与改验收规则是不同操作。若一个 DWG 中有多个图签，文件级验收失败也可能影响同文件的多行显示；详情中因此保留“可能涉及同文件其他图签”的说明。

## 5. 为什么文字、位置、布局会出问题
一个看上去相同的图签，内部可能存在不同结构：属性文字、富文本属性、散文字、嵌套块、外参或代理对象。程序对它们走的分支不同。

文字外观由多项参数共同决定：字体和文字样式、字高、宽度系数、对齐方式、插入点/对齐点、旋转、富文本宽度与换行，以及上层块变换。仅复制文字内容或仅保留块插入点，都不足以保持外观。

图框块定义的内部原点、边线位置和实际边界同样重要。两个块的插入点和缩放完全相同，内部边线仍可能不在同一位置。因此代码中的变换一致性检查，不等于完整验证实际图框边界与主体的相对位置。源码虽然包含边界与规格识别辅助逻辑，也不能因此宣称已经全面覆盖所有特殊基点、嵌套边界和视觉错位情况。

当前验收的规划外句柄清单检查，也不是对每个非目标实体的坐标、图层、颜色、视口和裁剪状态进行完整深度比较。这是后续扩大布局验证时需要明确的边界。

## 6. “原作者边界”分三层判断

### 6.1 仓库明确写出的开发规则
[开发与调试说明](../docs/开发与调试说明.md) 明确写出：
- 模型空间和布局空间分别识别。
- 布局炸开图框只在证明存在完整 ISO 外边界后处理，保留 VIEWPORT、裁剪多段线和非图签块。
- 无法确认图名、图号或删除目标时，标记待核对/失败，**“不允许静默叠写”**。
- 单文件失败不得中止整个批次。
- 修改识别/替换逻辑后，需要编译、脱敏 DWG 扫描、实际替换复扫、数量核对及原生 CAD 抽查。

README 规定仓库用于团队内部协作和 Debug，不应放入客户原图、未脱敏 DWG、处理输出、日志、凭据或本机配置。.gitignore 配合排除这些文件，但忽略规则不能代替人工检查。

这些是版本库留下的明确项目要求；不能仅凭文件内容认定每一条都由同一位原始作者亲自制定。

### 6.2 技术实现和产品范围体现的约束
以下是依据当前代码作出的工程判断：
- 继续利用已安装的 AutoCAD Core Console，不能把项目当作独立实现 DWG 引擎的软件。
- 识别依赖有限规格、标签和结构规则。无法识别应提示和保留核对入口。
- 业务层修改不应悄悄删除激活、设备绑定、签名检查或更新完整性检查。
- 替换目标和非目标内容应分清，尤其是布局视口、主体、外参和裁剪对象。
- 对外承诺“大小和位置不变”必须说明字段与结构范围，并以真实 DWG 验证。
- 提示更易懂可以改变说明方式；不能把失败记录改成通过来制造成功。

这部分是从架构和现有规则推导出的开发边界，不冒充作者另行签署的书面禁令。

## 7. 激活、密钥和更新：哪些地方维持原设计
许可系统采用设备绑定、RSA-SHA256 签名令牌以及 Windows 当前用户范围的加密缓存。默认设备数和离线窗口可由服务配置，代码默认分别为 2 台和 7 天；不是所有部署都必然相同。

私钥留在服务器，用于签发许可；客户端嵌入公钥，用于检查签名。公钥可分发不代表私钥可以公开。管理员令牌、用户数据库、设备信息和许可缓存同样不应随源码公开。

相对上述 main 基线，本包以下文件逐字节一致：
- build.ps1；
- src/CadProcessingCore/LicenseGuard.cs；
- src/Drawing100Wpf/LicenseWindow.cs、UpdateManager.cs、App.config；
- src/CAD100Updater/Program.cs；
- server 下全部 5 个文件；
- engine/assets 下素材及其校验清单。

这支持“本次差异集中在界面及图纸业务处理，相关独立授权/更新文件和素材未改动”的结论。它不是对修改过的业务文件作完整安全审计，也不证明作者的合同授权。

## 9. 后续怎样验证“仍在边界内”
建议每次变更形成一条可追溯记录：具体需求 → 涉及文件 → 写入对象范围 → 哪些保护规则保持 → 测试证据 → 对应构建程序。

本包试用说明记录了 10 项变换检查、54 个文字属性数据回放、验收元数据模拟和编译检查，并明确写明“以上数据模拟不等于实际处理了 DWG”。本次阅读没有重新执行这些测试，也没有启动 AutoCAD 实际处理样本。因此这些是随包记录，不能扩大成此次已证明所有 DWG 都正确。

真正完成新一轮验收，仍需要用你的原始脱敏样本运行对应新构建，在原生 CAD 中打开、保存、重开，并检查模型和布局、字号位置、比例单位、签字、外参和非目标内容。工程规则可以逐项核对；权利人未写下的意图不能由我替其保证。

## 10. 阅读顺序
先读第 2、3 节建立处理流程，再用第 4、8 节找文件，最后用第 6、7、9 节核对边界。无需先逐行阅读几千行源码。
